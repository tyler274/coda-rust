# The physician site and the Coda Agents harness

The shipping physician client is the React site in `submodules/coda-agents/web`. The Rust page is the Dioxus client in [`physician-app`](/crates/physician-app/src/lib.rs), mounting into `#main`, speaking the same projections through [`physician-wire`](/crates/physician-wire). [`physician-sample`](/crates/physician-sample/src/lib.rs) serves the page and the physician routes over the synthetic practice, with chat through the model execution described next; tests also use its recorded projection, and `PHYSICIAN_UPSTREAM` forwards physician routes to the Node server. Model execution is owned by [`local-product`](/crates/local-product/src/lib.rs); `api` mode is opt-in and never runs without an authorized key. [`agent-skills`](/crates/agent-skills/src/lib.rs) reads the clinical skill catalog in [`skills/`](/skills) for [`harness`](/crates/harness/src/lib.rs); only hosted chat in `physician-worker` loads it (see [Skills in hosted chat](#skills-in-hosted-chat)); the [`encoder`](/crates/encoder/src/lib.rs) runs the offline patient-text inference, and [`patient-work`](/crates/patient-work/src/lib.rs) models the dispatcher's grouping window.

## Product direction and proof

The <a href="/intent/physician%2Emd">physician spec</a> owns product intent, and the
[Coda Agents project](https://linear.app/coda-health/project/coda-agents-d7d16847168e)
tracks the work against it; each
journey's chart and Verus proof live under <a href="/verification/README%2Emd">verification</a>,
starting with <a href="/verification/physician/sign-in/README%2Emd">sign-in</a>. Verification
keeps design artifacts separate from runtime and clinical qualification. The
original repository links below are comparison evidence, not a competing
specification or a claim of current Rust completeness.

## Current execution paths

The page, identity, clinical execution and delivery each have an owner:

| Responsibility | Owner |
| --- | --- |
| Physician screens, navigation and command feedback | [`physician-app`](/crates/physician-app/src/lib.rs), through [`physician-client`](/crates/physician-client/src/lib.rs) and [`physician-wire`](/crates/physician-wire) |
| Sign-in, practice membership and panel access | [`physician-auth`](/crates/physician-auth/src/lib.rs), enforced at the site routes |
| Serving projections and accepting chat commands | [`physician-sample`](/crates/physician-sample/src/lib.rs) and its [`live`](/crates/physician-sample/src/live.rs) adapter |
| Physician model execution and conversation state | [`local-product`](/crates/local-product/src/lib.rs): `PhysicianSession` for inline execution; Postgres `runtime::Store` for queued execution |
| Waking accepted queued turns and executing them | [`durable`](/crates/physician-sample/src/durable.rs) and [`physician-worker`](/crates/physician-sample/src/bin/physician-worker.rs), through Pub/Sub |
| Telling open pages to reread changed state | [`physician-bus`](/crates/physician-bus/src/lib.rs), using a local bus or Redis fan-out |

With `PHYSICIAN_CHAT_TOPIC` unset, `live` opens
[`PhysicianSession`](/crates/local-product/src/execution.rs) for chat and reply
work, using a local session file outside test fixtures. The model mode selects
Codex CLI, cassette recording/replay or opt-in Responses API execution; see
<a href="/README%2Emd#physician-chat-codex-cli">local chat setup</a>.

With `PHYSICIAN_CHAT_TOPIC` set, the site accepts and reads chat through the
Postgres [`runtime::Store`](/crates/local-product/src/runtime.rs), and the worker
runs the accepted turn. This requires `PHYSICIAN_DATABASE_URL`; setting the
database alone still leaves chat inline. [Scaling across instances](#scaling-across-instances)
describes acceptance, recovery, fan-out and the current reply-revision limit.

The synthetic practice's recorded projections and the live chat path are separate
evidence. A rendered summary, Today row or recorded draft does not establish that
the Rust runtime produced that clinical work. Likewise, a completed chat does not
establish all the graph's review, preparation, follow-up and communication paths.
Use the [implementation coverage](#product-direction-and-proof) to find those gaps.

### Choose the proof for the claim

| Check | What it can establish | Boundary |
| --- | --- | --- |

## Physician sign-in and practice access

[`physician-auth`](/crates/physician-auth/src/lib.rs) is one durable owner for who a clinic user or physician is, which practice they belong to, who holds panel-assignment permission, and which patients are on each physician's panel. Sign-in is a per-user email magic token: the server issues a one-time token (24-hour TTL, stored `sha256`-hashed), and its verification mints one bearer session (30-day TTL) with a revocation fence (`sessions_ended_before`) so deactivating an account ends every session it holds.

Access follows three concentric boundaries:
1. **Practice boundary (cross-clinic isolation):** Any patient or workspace outside the signed-in user's `practice_id` answers 404 — never 403 — and never appears in roster search.
2. **Clinic demographic boundary (same clinic, not on the physician's panel):** Physicians and staff in the clinic can search the clinic's patient roster and read basic demographic information (`display_name`, `birth_date`, `age_years`, `sex_or_gender`, `medical_record_numbers`) on `GET /patient-workspaces/{id}` for other patients in their clinic, while clinical synopses, citations, chats, follow-ups, Today items, drafts, and commands remain omitted/404.
3. **Panel clinical boundary (`Membership::Allowed`):** Full clinical workspace reads, Today items, chat snapshots, drafts, and commands require the patient to be assigned to the physician's panel. Clinic admins, secretaries, and physicians holding the `admin` permission can assign or remove clinic patients on a physician's panel via `PUT /auth/panels/{physician_id}/{patient_workspace_id}` (`AuthStore::assign_panel`).

The store is the [`AuthStore`](/crates/physician-auth/src/lib.rs) trait over SeaORM and PostgreSQL: `physician-sample` holds `Arc<dyn AuthStore>` and picks the Postgres store (connecting without applying migrations; the migration job owns schema changes) when `PHYSICIAN_DATABASE_URL` is set, process memory otherwise. With `PHYSICIAN_AUTH=required`, one Axum middleware guard resolves the bearer session before any physician read and enforces the practice, clinic-demographic, and panel boundaries before any patient read or command dispatch; the auth routes and `/health` stay open. The physician client in [`physician-app`](/crates/physician-app/src/lib.rs) carries the bearer session on every read through [`physician-client`](/crates/physician-client/src/lib.rs) and shows an email form followed by “Check your email” before any physician data renders. Clicking the email’s Sign in button removes the token from the URL, redeems it automatically, and opens Today without a code field or second confirmation. Used or expired links offer a new link; verification transport failures remain distinguishable from an invalid link. Local proof delivery redeems its returned token through the same client path without exposing it in the page.

The retained GKE deployment reference is <a href="/infra/gcp/physician-runtime/README%2Emd"><code>infra/gcp/physician-runtime</code></a>: one private GKE Autopilot cluster, one private Cloud SQL Postgres 16 instance with IAM database authentication (no database password), separate keyless site and migration identities, and `PHYSICIAN_AUTH=required` riding the site's environment as configuration intent. The current isolated Rust staging path is Cloud Run under [GCP deployment](gcp.md#rust-staging-bootstrap-and-deployment-gate); configuration is not hosted access proof.

## Scaling across instances

A turn that finishes on one `physician-sample` instance has to show up on a stream another instance is holding open. [`physician-bus`](/crates/physician-bus/src/lib.rs) is the physician product's fan-out. It carries `workspace_changed`, `workspace_settled`, and `resync`. `resync` is what a subscriber gets when it lags or the connection drops, and the Dioxus client refetches on that event. Sign-in and panel changes stay on the existing Postgres `NOTIFY` feed, which also fires for the migration job and for `psql`.

`RedisBus` is the `fred` client: TLS plus AUTH, `PHYSICIAN_REDIS_URL` as a `rediss://` URL and `PHYSICIAN_REDIS_CA_PEM` as the Memorystore server CA. With `PHYSICIAN_REDIS_URL` unset, `LocalBus` keeps those events inside one process. That is the local and test path.

Hosted `message.submit` accepts the turn in Postgres and publishes `{scope, input_id}` on the Pub/Sub topic `physician-chat-turns`. The topic carries only that pair. `physician-worker` checks the push token's audience and the `physician-pubsub-push` email, claims the leased turn, runs the model, commits, and publishes `workspace_changed`. A non-2xx response is a redelivery. After 5 attempts the message goes to the dead-letter topic. The subscription's ack deadline is 600 seconds, and retries back off from 10 seconds to 600 seconds.

When a push cannot claim its turn, the worker answers from the saved conversation. It acknowledges a turn that is committed, stopped, replaced by a newer message, or running under another live claim. It answers 500 for a turn that is still waiting and for one that recovery gave up on. The second case is what lets Pub/Sub dead-letter the message: it counts each message's own deliveries, so a message the sweep republished under a new ID still reaches the dead-letter topic.

The worker publishes `workspace_changed` after each committed reply and each failed attempt, including a provider that cannot start and a push that finds the turn already failed. That last case covers a turn whose worker leases all ran out: the claim records the fifth failure and nothing is left to run. A held page then refetches and shows "Coda couldn't finish". The site's recovery sweep republishes accepted turns whose wakeup never reached the topic, so a turn accepted by an instance that died is finished by whichever instance is still up. [`tests/instance_loss.rs`](/crates/physician-sample/tests/instance_loss.rs) proves both against the emulator, Valkey and Postgres.

Outside hosting, `PUBSUB_EMULATOR_HOST` turns off push-token checks, because the emulator sends no token. The worker then starts only on a loopback listener (`127.0.0.1` or `[::1]`). `PORT` alone binds `0.0.0.0`, so it, a wildcard, or any other address refuses to start. Hosted runs refuse the emulator setting altogether.

The site queues turns only when `PHYSICIAN_CHAT_TOPIC` is set. Without it, hosted or not, chat runs inline in the site process as it did before the worker, and a hosted start logs a warning. `PHYSICIAN_CHAT_TOPIC` without `PHYSICIAN_DATABASE_URL` refuses to start, because the turn is accepted in Postgres.

| `PHYSICIAN_CHAT_TOPIC` | `PHYSICIAN_DATABASE_URL` | Startup |
| --- | --- | --- |
| unset | unset | Chat runs inline. Hosted logs a warning. |
| unset | set | Chat runs inline. Hosted logs a warning. |
| set | unset | Refuses to start. |
| set | set | Turns go to Postgres and the topic. The worker runs the model. |

With the topic set, reply revision also runs in the worker. Drafts live in `physician_runtime_reply_drafts`, one JSONB row per practice, physician, workspace and reply, which [`Store::migrate`](/crates/local-product/src/runtime.rs) creates from its SeaORM entity. `GET` and `PUT /replies/{id}` read and save that row; a save must name the current revision, and a `PUT` never creates a draft. `reply.revise` checks the session and workspace, then `Store::accept_revision` records the instruction, the saved text it applies to and the workspace's current source revisions with their version, read in its own transaction, and the site publishes a `reply_revision` delivery on the chat-turn topic. The same command id returns the same acceptance and publishes nothing new. A draft that is missing, belongs to another physician, has moved past the command's expected revision, or already has a revision in progress refuses with 409.

The worker claims the draft and runs [`revision.rs`](/crates/physician-sample/src/bin/physician-worker/revision.rs) through `harness::execution::run`. It has two tools: `read_patient_sources`, which answers only from the attempt's pinned sources, and `finish_reply_revision`. Each model exchange is saved on the draft before the next one. A retry reuses the same instruction and base text, pins the newest sources when it is claimed, and starts from the calls and tokens its revision's earlier attempts already spent, so the eight-call bound covers the whole revision.

Anything Coda is still working on takes in what arrives before it finishes, so nothing it produces rests on an older reading. A reply under revision is still a draft; its history is fixed only once something is said or sent. `Store::commit_revision` therefore compares the attempt's source version with the workspace's current one in the transaction that would publish, under the draft lock, the auth owner's locks and a shared lock on the source version row. If they differ, nothing is published. The attempt records a `SourceRefresh` (from and to version, added, corrected with the earlier revision kept, and withdrawn sources), the draft re-pins, and the model receives a `sources_changed` result naming those references. It reads them and finishes again in the same run, under the same eight-call bound; a catch-up is not a failed attempt. A finish whose context does not yet hold an exact read of every added or corrected source, at its current revision, gets `sources_unread` instead. If the chart keeps changing until the bound runs out, the revision ends as failed and the saved draft is unchanged. The attempt's `sources` stays what it claimed and its `refreshes` show what it could read afterwards, so the record lists only sources Coda could actually read. Inline sites apply the same rule in `LiveOwner::finish`, over a versioned in-memory observation under the publication guard. Chat turns read no patient sources yet; the same check applies once they do.

Hosted sources live in a stand-in source store, `physician_runtime_sources` and `physician_runtime_source_versions` ([`runtime/sources.rs`](/crates/local-product/src/runtime/sources.rs)). Each site imports the `CODA_PHYSICIAN_SOURCE_SNAPSHOT` file at startup through `Store::import_sources`; a correction or withdrawal is a new row, never a rewrite, and the workspace's version moves only when what can be read changes. A revision identity is immutable within its workspace and candidate: different content or provenance under an already recorded identity is refused, including after correction or withdrawal. Replaying any identical historical revision is a no-op, so an older instance's startup snapshot cannot roll back a correction or resurrect a withdrawal. Restoring a withdrawn candidate requires a previously unseen revision identity; opaque revision strings are not sorted to infer age. The inline observation follows the same rules for its process lifetime. Catch-up checks compare the exact native content, hash and provenance as well as revision identity, not just a matching revision label. `Store::record_source` and `Store::withdraw_source` are its only other entry points, used by tests. Projection prose and model output never become sources, and this is not production ingestion. Completion commits under the physician's current session authority and the draft revision accepted with the command. If the physician saved a newer draft in between, the late completion is refused and their text stays. A failed attempt returns the revision to pending and answers 500, so Pub/Sub keeps counting toward the dead-letter topic; the fifth failure ends the revision as failed. The draft `GET` returns `revision_run`, the latest accepted command id and its status (pending, active, completed, failed or superseded), so a failed revision is visible, not only stored. Accepting another revision moves the previous one, with its sources and every attempt's records, into `physician_runtime_reply_revisions` in the same transaction, one row per earlier revision. The draft row holds only the current revision, so its size does not grow with history. A history row changes only when a superseded attempt's worker records a late exchange, observation or failure; that record is appended to the archived attempt and cannot publish or alter the current draft. Each row carries a per-draft ordinal assigned under the draft lock, and `Store::earlier_revisions` reads one physician's draft oldest first by that ordinal. The recovery sweep republishes due revisions just as it does turns.

The composer saves the physician's unsent chat text through `GET` and `PUT /physician-state/drafts/{workspace}/{chat}`. With no chat open the page saves under the chat id `draft`. [`chat_draft.rs`](/crates/physician-sample/src/chat_draft.rs) serves both. On a hosted site the draft is a row of `physician_runtime_chat_drafts`, keyed by practice, physician, workspace and chat, with typed `text` and `revision` columns, which `Store::migrate` creates from its SeaORM entity. [`Store::save_chat_draft`](/crates/local-product/src/runtime/chat_draft.rs) checks the physician's session and panel in the save's own transaction. It inserts revision 1 only when the page names revision 0, and otherwise updates only the revision the page names. A stale save writes nothing and answers 409 with `{outcome: "conflict", current}`, so one instance's save is read and fenced by every other instance. Inline sites keep the same draft in `PhysicianSession`, under a target key that cannot collide with a chat's or a reply's own target, so a saved draft never fences the chat's turns. On a hosted site a missing session answers 401; an inline site with sign-in off keeps one anonymous local draft, as it does for anonymous chats. A patient outside the physician's panel answers 404, and another physician on the same patient has a separate draft. The recorded and simulation routers still answer 409, because their projections are read-only.

[`composer.rs`](/crates/physician-app/src/composer.rs) holds the page's draft state as pure, unit-tested transitions. Each patient and chat keeps its text, an edit generation, the acknowledged revision and text, at most one save in flight, any Send still being confirmed or cleared, and the conflict the physician has not yet decided. There is no Save button. Typing saves about 800 ms after the physician pauses, and leaving the box saves at once. A save names the revision this tab last saw, and its result is fenced to the chat and edit generation it carried: a late result never marks another chat and never replaces newer typing. Typing during a slow save gets a trailing save when it returns. When this tab's own save advances the revision, later edits rebase onto it instead of reading as another tab's conflict. A failed save shows "Not saved" and tries again on a growing delay, never in a tight loop. The client decodes a conflict only from a validated `{outcome: "conflict", current: {revision, text}}` body; a bare or malformed 409 is an ordinary failure and never authorizes an overwrite. A conflict pauses autosave and shows the newer text with two choices. **Retry** replaces the saved draft with this tab's text over exactly the revision shown, and shows another conflict if it moved again; the page never fetches the latest revision to overwrite it quietly. **Use newer text** takes the saved text into the composer and discards this tab's edit.

The Send button and Cmd/Ctrl+Enter share one path, which captures the chat, text, edit generation and `message.submit` command id; Check again reuses that capture. Acceptance removes only the submitted text, so text typed after Send stays. The saved draft is then cleared behind any outstanding save, including a first save at revision 0, naming the revision that save produced. If another tab saved newer text first, the clear stops and keeps that text: the message stays accepted and the draft is not erased. An accepted message and a failed draft cleanup are reported separately, and neither resends the message.

[`local_draft.rs`](/crates/physician-app/src/local_draft.rs) keeps unsent text across a reload of the same tab, in `sessionStorage` only. Closing the tab or the browser loses it; nothing is kept in `localStorage`. A record holds the text, baseline revision, edit generation and any Send or clear still being reconciled. Its versioned key is a JSON array of backend, practice, physician, workspace and chat, followed by the writing page's id. `sessionStorage` already belongs to one tab, and a reload reads the newest record any page of that tab wrote for the chat. The page restores only under a known physician and only after that physician's workspace read succeeds. A failed draft read keeps the record rather than treating the draft as empty. Restored text that matches the server, as after a save whose answer was lost, becomes the baseline without another save. Restored text over a revision the server has since passed shows the conflict choices. A Send whose acceptance was unknown at reload is asked again with its original command id before the text counts as unsent, so the message appears once; a pending clear is kept until it is confirmed. Sign-out, another physician's sign-in and removed workspace access delete the records. When storage is denied or full, the text stays in memory and the page says reload recovery is unavailable.

[`tests/chat_draft.rs`](/crates/physician-sample/tests/chat_draft.rs) proves cross-site reads, stale-save conflicts, Retry over the revision shown, lost-answer rebasing, the post-Send clear that never erases newer text, and physician ownership with two sites and disposable Postgres. `scripts/check-postgres.sh` runs that suite and the runtime draft-fence test. The Chromium journeys in [`tests/site.rs`](/crates/physician-sample/tests/site.rs) cover the Saved mark, a stale tab's conflict, a held save that ends after navigation, reload before the debounce and during a held save, a lost save answer, another writer's newer revision, sign-out, denied storage, keyboard Send with typing while the command is in flight, and a reload that asks again with the same command id. Run browser qualification explicitly with `cargo test -p physician-sample --test site -- --ignored --test-threads=1` (the browser CI job does this separately from the default test run).

`PHYSICIAN_SYNTHETIC_REPLY=1` turns on a synthetic reply source in [`synthetic_reply.rs`](/crates/physician-sample/src/synthetic_reply.rs). It is off by default and applies only to a signed-in physician of the synthetic practice (`roger-synthetic-practice`) on its first recorded workspace. The workspace read then carries one fixed-ready reply with a stable server-owned id and non-PHI wording. If the physician has no draft for it, the site opens revision 1: on a hosted site through `Store::open_draft_authorized`, which holds the physician's session, account and panel locks in the insert's own transaction; inline under the same publication fence that guards chat turns. Opening again, from any instance and concurrently, keeps the saved text and revision history. `PUT /replies/{id}` and `reply.revise` still refuse a reply that has no opened draft, and nothing is created from a browser payload. The reply card shows the saved text, its exact `draft_revision` and the latest revision run's status: pending, active, completed, failed (the saved draft is unchanged) or superseded (a newer saved edit won). Ask Coda to revise names the revision on screen. The hosted worker announces `workspace_changed` after completing or failing an attempt, and the page rereads the workspace; a missed notice is recovered by the existing resync after the bus reconnects. The card does not offer Send to the patient, and closing it is not supported in this mode. [`tests/reply_revision.rs`](/crates/physician-sample/tests/reply_revision.rs) signs in through Chromium on two hosted sites with Postgres, Valkey, the Pub/Sub emulator and the physician worker. It revises from the displayed revision on one site and sees the worker's wording on both. It also checks a stale revision refusal, a worker failure through `[fail:K]` with a Valkey restart in between, and a reload. With the switch off, no reply appears.

`GET /patient-workspaces/{id}` lists the signed-in physician's runtime chats for that workspace, newest activity first, each titled by its first physician message (cut to about 60 characters). Durable chats come from `Store::chats` over `physician_runtime_conversations`, scoped by practice, physician and workspace. Postgres orders them by latest activity, then chat id, before taking the newest 200, so a chat that just got a message lists however many older chats the workspace has. Inline chat submissions, lists, snapshots and completions use the same practice and physician identity in `PhysicianSession`. Existing unscoped session records remain local anonymous data; signing in does not assign them to that physician. Durable conversations record `opened_at` and `last_activity_at` in their JSONB state, so no migration is needed. The page's `New conversation` button, in the Conversations sidebar and the empty Conversation region, opens a new `chat-…` id. The navigation owner keeps `?patient=` and `?chat=` aligned with the selected conversation, including sidebar selection and patient changes, and removes both when leaving the patient page. A chat is listed after a reload once its first message is accepted.

The physician site sets `cpu_idle = false` so the Redis subscriber and the Postgres listener keep running between requests. The worker stays on request-based CPU: the push request is the turn. Duet has no Redis instance and no chat-turn topic.

Memorystore Basic 1 GB is about $35/month and the site's minimum instance about $48/month after the free tier. Dev raised the `coda-rust-stg` budget alert from $10 to $200/month before applying. Nothing is applied without a reviewed saved plan. An operator writes `PHYSICIAN_REDIS_URL` into the Doppler config `stg_physician_runtime`. The activation steps, including the CA bundle and the cost table, are [Physician scaling](gcp.md#physician-scaling-redis-fan-out-and-pubsub-chat-turns).

`nix develop` provides `valkey` and the Pub/Sub emulator (`google-cloud-sdk` with the `pubsub-emulator` component, and `jre_headless` to run it). The scale tests start it through the shared `pubsub::testing::Emulator` ([`crates/pubsub`](/crates/pubsub/src/testing.rs)); [`tests/scale/mod.rs`](/crates/physician-sample/tests/scale/mod.rs) only adds the chat-turn topic, push subscription and dead letter.

The bus proofs in [`tests/redis.rs`](/crates/physician-bus/tests/redis.rs) do not race production timing. `RedisBus::connect_with` takes a test `Timing` (heartbeat, command timeout, reconnect backoff and jitter); `connect` keeps the production values. The fast-restart proof routes the bus through a TCP proxy that the test closes and reopens, with a 60 s heartbeat and no jitter, so only the reconnect path can resync. Each test waits for the bus to be live and quiet instead of sleeping a fixed time.

The local worker can fail chosen messages. With `PHYSICIAN_WORKER_FIXED_TEXT` set, `PHYSICIAN_WORKER_FIXED_FAIL_MARKER=1` makes a message containing `[fail:K]` fail its first K attempts, counted from the attempts Postgres saved on that message, so a worker restart or a second instance keeps the count. Try again keeps the message, so `[fail:5]` dead-letters and its Try again answers. Hosted execution refuses the variable, like the other fixed-provider variables.

## Skills in hosted chat

Hosted chat in `physician-worker` offers one tool, `skill_view`. At startup the worker loads the clinical skill catalog in [`skills/`](/skills) once through [`physician_chat::PhysicianSkills`](/crates/local-product/src/physician_chat.rs), which wraps `harness::Harness` and adds no reader of its own. Hosted startup requires `PHYSICIAN_SKILLS_DIR`; the worker image sets it to a store path holding only `skills/`. A local worker defaults to this workspace's `skills/`. A missing or invalid catalog stops startup, so the worker never serves with an empty one. Every turn shares that one in-memory copy.

Each model request carries the physician-owned instructions `physician_chat::INSTRUCTIONS`, versioned by `INSTRUCTIONS_VERSION`, followed by the catalog metadata: names, descriptions, version ids and resource paths, but no bodies. The model reads a body or a listed supporting resource with `skill_view(name, file_path, max_result_bytes)`. `name` is required, `file_path` must be present and is `null` for `SKILL.md`, and `max_result_bytes` is 4096 to 65536. An unknown tool or malformed arguments come back to the model as `{"executed": false, "error": ...}` without running; an unknown skill comes back `unavailable` and a result that does not fit comes back `over_budget`, never partial. A bad call does not stop a valid read in the same turn. A skill is guidance only; it grants no tool, patient read or action. The local Codex CLI path keeps `codex::PHYSICIAN_CHAT_INSTRUCTIONS` and offers no tools.

A turn may make up to 8 model calls and 16 tool calls, 8 per model response. One result may be 65536 bytes and a turn's results 262144 bytes. Every request (with its exact instructions and tools) and every tool result (with the skill's `version_id`) is saved on the attempt before the next step, as for other runtime events.

The engine's candidate text joins assistant text from every round, including narration before a tool call. `Store::commit_authorized` does not publish it. It publishes the text of the attempt's last recorded model response, which must contain no tool call and some text; several text parts in that response are joined in order. A blank final response publishes nothing and fails the commit, rather than falling back to earlier narration. The authorization, lease, revision and stale-commit checks are unchanged. Reply revision keeps its own tools and is not affected.

[`tests/runtime_postgres.rs`](/crates/local-product/tests/runtime_postgres.rs) and [`tests/runtime_publication.rs`](/crates/local-product/tests/runtime_publication.rs) prove this against Postgres. In [`tests/worker.rs`](/crates/physician-sample/tests/worker.rs), `PHYSICIAN_WORKER_FIXED_TOOL_ROUNDS` scripts the fixed provider's tool calls before its fixed text, so the real worker, emulator and Postgres run skill reads, refused calls and a supporting-resource read before the answer. Hosted execution refuses that variable. [`scripts/check-images.sh`](/scripts/check-images.sh) checks that the worker image carries every catalog file and that the packaged worker refuses to start without its catalog.

## Retention

The physician runtime keeps clinical history and the evidence Coda can learn from; only disposable copies expire, after 90 days. HIPAA sets no single record period, so clinical history follows the practice's own record schedule. No automatic deletion runs until that schedule exists. The rows below are the hosted Postgres copies, plus the copies kept outside the runtime.

| Copy | Owner | Purpose | Rule |
| --- | --- | --- | --- |
| Conversations (`physician_runtime_conversations`) | [`runtime::Store`](/crates/local-product/src/runtime.rs) | Clinical history: what the physician asked and what Coda answered | Kept under the practice's record schedule. No automatic deletion. |
| Chat drafts (`physician_runtime_chat_drafts`) and reply drafts (`physician_runtime_reply_drafts`) | [`chat_draft.rs`](/crates/local-product/src/runtime/chat_draft.rs), [`reply.rs`](/crates/local-product/src/runtime/reply.rs) | The physician's unsent text; for replies, the current revision with its instruction, base text, pinned sources and attempts with their source refreshes | Kept under the practice's record schedule, including a reply's last revision when no later one replaces it. |
| Earlier reply revisions (`physician_runtime_reply_revisions`) | [`reply.rs`](/crates/local-product/src/runtime/reply.rs) | Learning evidence: what Coda could read, what it read and produced, and what the physician changed | Append-only: a superseded attempt's late records are added, nothing is rewritten; kept with clinical history until the de-identified learning export exists. |
| Patient sources (`physician_runtime_sources`) and their versions (`physician_runtime_source_versions`) | [`sources.rs`](/crates/local-product/src/runtime/sources.rs) | The stand-in source store: every revision of each source a reply revision could read, and each workspace's observation version | Append-only: corrections and withdrawals are new rows. Kept with clinical history, since pinned and refreshed revisions on drafts and earlier revisions refer to them. |
| Execution records (attempt records on conversations and drafts) | [`runtime::Store`](/crates/local-product/src/runtime.rs) | Model requests and responses, tool reads, failures, and the evidence retries and recovery replay | Kept with the record they belong to. |
| Command receipts (`physician_runtime_commands`) | [`receipt.rs`](/crates/local-product/src/runtime/receipt.rs) | Idempotency: a repeated command id returns the same answer; a different command under that id is refused | Full command for 90 days from `accepted_at`, then reduced to a salted digest. |
| De-identified learning episodes | Not built | Long-term learning from whole episodes | Blocked until agreements grant the source rights and a validated de-identification process exists. |
| Langfuse traces | [Observability](observability.md) | Debugging model runs | The self-hosted deployment keeps them for 90 days. |

Command receipts duplicate input the runtime already keeps: a chat message lives in its conversation, and a reply instruction lives in its draft or archived revision. After 90 days, `Store::compact_receipts` replaces the stored command with `{"salt", "sha256"}`: a random salt kept on the row, and the SHA-256 of that salt followed by the command's canonical JSON (keys sorted). A repeated command still gets its original answer, and a different command under the same key is still refused. Rows that existed before `accepted_at` was added count their 90 days from the migration. The hosted site's recovery sweep runs compaction on start and then hourly, in batches of 100 receipts, at most 2,000 per run.

Sources carry their own limits. Under Google's Workspace user-data policy, Gmail-derived content cannot train shared models, even when it is de-identified or rewritten. Duet's data stays with Duet's owners; its separate consent rules apply, and nothing here reads it.

Not yet built:

- **Learning export.** Without it, nothing de-identified exists to keep after a clinical deletion. A failed export cannot justify keeping PHI indefinitely.
- **Per-practice record schedule and deletion.** No scoped deletion, withdrawal or offboarding path exists for runtime rows.
- **Backups and restores.** Cloud SQL backup expiry is not set from this policy, and a restore could bring back rows deleted after the backup was taken.
- **Diagnostic copies elsewhere.** Datadog logs and traces, and other operational stores, follow their own owners' schedules.

## Remaining gaps

- **Production reply work.** The only live source of reply work is the opt-in synthetic one above, a fixed scenario on one synthetic workspace. No inbound patient message is ingested, no clinical first draft is generated, nothing is delivered to a patient, and close, send and supersession are not offered for that reply. A real reply owner must open drafts through `Store::open_draft_authorized`, as the synthetic source does.
- **Patient source ingestion.** Sources come only from the retained snapshot file through the stand-in store. No EHR, lab or message feed records or withdraws them in production.
- **Editing a reply in the page.** The reply card is read-only. `PUT /replies/{id}` saves over an existing revision, but the client does not edit through it, and restoring Coda's earlier text is not offered.
- **Recovery after the tab closes.** Unsent composer text survives only a reload of the same tab, plus whatever autosave already stored on the server.
- **The rest of hosted chat ([ENG-159](https://linear.app/coda-health/issue/ENG-159)).** Hosted chat reads skills only. It cannot read patient sources or qualify citations, search literature, write patient memory, delegate, or show run steps, and inline (non-worker) chat and the local Codex path load no catalog. `harness::engine` owns the shared model/tool loop; `harness::execution` retains the compatibility API and durable record shapes used by revisions and inline execution. Loop consolidation does not qualify the remaining clinical capabilities. No real-provider run with skills has been recorded.
